# Donpa reuse audit

Reviewed 2026-09-30 for the [preflight spike](../spikes/preflight-open-source-reuse.md). **Decision: use as an architectural reference only.** No Donpa package, source, assets, identifiers, or release tooling is proposed for inclusion. Relevant work: Epics 01, 02, 04 and 07, with save durability questions carried into Spike 03.

- Repository: [vlumi/donpa](https://github.com/vlumi/donpa).

- The manifest, test/build/generation scripts and generated-project post-build hook were inspected before execution. The package has no external packages or build plugins. The test script invokes `swift test`; the build hook writes a commit identifier into the built product's plist. Release/upload commands were not run.

The audit's shallow clone already resolved to this exact hash; future moving HEAD is not the reviewed input.

The first package-test attempt failed because the sandbox could not write `/Users/d/.cache/clang/ModuleCache`. The same command was rerun with approved escalation and **passed**. Durable excerpts from that run:


The three skips are opt-in guide/medal image generators requiring output-directory environment variables. This is 683 reported tests, including three skips, with zero failures. The compiler reported concurrency warnings in tests, `LaunchStores` and `BoardScene+MinimapImage`, including warnings that become errors in Swift 6 language mode; it also warned about the missing explicit Combine import in `GameContent`. A Swift 6.4 compiler pass under the package's Swift 5.9 manifest is **not** evidence of Swift 6 language-mode readiness.

**App-build blocker:** XcodeGen is not installed, no `.xcodeproj` is committed, and `Scripts/generate.sh` exited 1 with `error: xcodegen not found (brew install xcodegen).` Its preceding process check also reported sandbox process-list restrictions, but continued to the missing-tool check. No tool was installed to resolve this secondary build prerequisite. Both iOS and macOS application builds therefore remain unverified; package compilation and tests do not constitute app, simulator, accessibility, or device validation. [Build configuration and scripts][build] describe the reproducible next step: install an explicitly pinned XcodeGen, generate the project, then run unsigned `xcodebuild build` for schemes `Donpa-macOS` and `Donpa-iOS`.

## Runtime data flows and capability boundary

These are **static code findings**, not packet capture or proof of observed network activity. Searches covered runtime Swift source, plists, entitlements and the package manifest. No direct URLSession/URLRequest client, ad SDK, attribution SDK, crash-reporting SDK, remote configuration, push registration, tracking request or in-app purchase flow was found. Absence of those clients does not make the full application compliant with the product rules.

| Flow | Evidence and product implication |
| --- | --- |
| Local saves and progress | [`SaveStore`][save] writes compressed, versioned JSON snapshots to Application Support; defaults store settings, score aggregates, daily history and achievements. Friends have local storage. These are local game state, but only state needed by GameCore progression should be retained. |
| Cloud scores, achievements, daily results, friends and device metadata | Concrete `NSUbiquitousKeyValueStore` adapters are compiled into **DonpaCore**, including `CloudStatsStore`, `CloudAchievementsStore`, `CloudDailyStore`, `CloudFriendsStore`, device registry and nickname stores. Both [platform app entry points][platform] construct `UbiquitousStatsStore` for ordinary launches, whose initializer calls `synchronize()`; score-sync off does not remove the adapter or its initialization. The UI test clean-launch flag injects nil instead, but is not an appropriate production privacy boundary. |
| Game Center and its preferences | [`GameCenterReporter`][support] authenticates and reports earned achievement/progress snapshots when enabled. [`GameCenterPrefs`][gcprefs] separately synchronizes enabled/asked/timestamp state through iCloud KVS **outside the score-sync gate**, initializes KVS on ordinary launch and pushes a declined prompt decision as well. This directly contradicts treating “score sync off” as “no cloud calls.” |
| Nearby sharing and identity | [`NearbyExchange`][nearby] advertises/browses Bonjour peers and exchanges signed score-card URLs over encrypted MultipeerConnectivity sessions after the handshake. Cards include a display name and scores, with optional career data. `ShareIdentityStore` uses a synchronizable Keychain item. Core contains signing/codec/link/merge logic; removing only the sharing screen leaves reusable package scope unnecessarily large. |
| Camera, files, links | iOS declares camera and local-network usage descriptions; both platforms advertise `_donpa-swap` services and the `donpa.app` associated domain. QR scanning uses AVCapture; macOS permits user-selected read/write files. Local decoding of a payload URL is distinct from a network request, but the associated-domain capability and external help/about links are still unnecessary here. |
| Entitlements | [Both targets][entitlements] enable Game Center, iCloud KVS and associated domains. macOS additionally enables sandbox network client/server and selected-file read/write. Use newly authored minimal entitlements, rather than copying and toggling these off in UI. |
| StoreKit and diagnostics | StoreKit is used for a review prompt, not a discovered purchase implementation. [`InputTrace`][trace] records public-level OS log messages when explicitly enabled by a diagnostic launch flag; it is not a discovered remote telemetry SDK. Exclude that title-specific diagnostic path from any slice. |

The July 6 [privacy policy][privacy] describes optional cloud/peer features but does not document the later Game Center preference flow. Code is the evidence for this audit; that policy must not be copied as GameCore's privacy statement. Tooling's GitHub/Codecov/App Store Connect traffic is separate from shipped application traffic and was not classified as an app SDK.

## Small reusable slice and decision rationale

The smallest credible extraction candidate is **recorded elapsed time → formatted current/best labels → displayed improvement**, for the shared shell/progression UI in Epics 02/04. Its source allowlist would be [`TimeFormat.swift`][timeformat] plus [`TimeFormatTests.swift`][timetests], with the test import renamed to our module. The formatter uses Foundation and integer arithmetic only; its tests use XCTest and that formatter, with **no transitive Donpa source, resources, cloud adapters or package dependency**. The ten upstream tests passed in this audit. An original SwiftUI demonstration would supply explicit elapsed/best values and display the formatter output; neither the Donpa timer nor scoreboard would be copied. Only local own-score comparison is relevant; the rival-gap helper can be omitted. Negative/oversized input handling and localized/accessibility labels would need our own contract and tests.

Estimated cost for that exact extraction: **0.25–0.5 developer day** for attribution, a module wrapper and demonstration, plus **0.25–0.5 day** for input-boundary, localization and integration tests. An original implementation of the same small requirement is also **0.5–1 day including tests**. Copying therefore offers no persuasive schedule advantage and the reference-only decision stands. These are planning estimates, not work already performed.

A larger architectural reference is **move → immutable snapshot → local atomic save → resume**, with a scene hosted by a platform wrapper. The rules/UI module split and thin app entry points are good references. However, Donpa uses custom `UIViewRepresentable`/`NSViewRepresentable` SKView wrappers ([BoardView family][boardview]), not simply a generic SwiftUI SpriteView host. Its rules module also includes cloud adapters, persisted social/device state and keychain access, so it is not suitable as GameCore's package dependency.

Study the 259-line `SaveStore`, 124-line `GameSnapshot`, the 361-line `SaveStoreTests`, `BackgroundSaveWriter`, and the lifecycle hooks in [`GameContent`][content]. Then implement a small original title-neutral snapshot envelope/store with injected storage and a first-party scene adapter. Keep only the design ideas: independently testable state, immutable snapshots, explicit lifecycle saves, corruption/version checks, and a shared save-store instance for list and gameplay consumers. Use original names, fixtures, save magic and title namespaces.

Extraction/adaptation estimate: **1–2 developer days** for the small sample slice plus **0.5–1 day** for focused save/lifecycle tests, assuming the platform spike supplies a buildable shell. This is a planning estimate, not time already spent or a claim of production durability. A literal extraction is unlikely to save time: `GameSnapshot` and summaries depend on Minesweeper configuration, cells, status and daily keys; the store silently ignores failures, sanitizes keys without collision-resistant title namespacing, uses unbounded decompression, and writes the summary separately from the main snapshot. Two separately atomic writes are not a transaction. Background actor writes and synchronous exit writes also deserve explicit ordering tests in Spike 03 rather than inherited guarantees.

Test the new slice for title isolation, unknown/newer versions, corruption, failed writes with the previous valid save preserved, interrupted main/summary writes, stale pending snapshots after restart/clear, and pause/termination ordering. Device termination behavior remains a target-hardware test, not something the upstream unit result settles.

**Maintenance owner:** GameCore's shared-core maintainer for Epics 01/02/04; the release/platform maintainer owns capability checks. These are role assignments pending named project ownership. Upstream's recent commit, multi-release changelog, extensive unit suite and two-platform CI configuration are positive maintenance signals; this audit did not establish contributor depth, response SLA or the latest remote CI outcome. The repository is a single title with its own roadmap, so upstream maintenance does not replace ownership of a generalized local-only core.

**Reversal cost:** negligible now because no dependency or source is imported. After an original prototype, changing the scene adapter should be bounded to its module seam; changing a shipped save format requires migration and cannot be called cheap. Reconsider licensed extraction only for an isolated algorithm with demonstrated benefit, a file-level inclusion list, passing tests and no cloud/resource dependency. Do not adopt the app wholesale.
