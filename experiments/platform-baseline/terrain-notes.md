# Disposable terrain investigation

The original `TerrainHeightfield` simulation lowers a radial patch of a 25 × 25 grid, clamps depth at 0.45 scene units, and leaves topology unchanged. It has no rendering dependency. Each command rebuilds a 625-vertex, 1,152-triangle mesh with `MeshDescriptor`, then separately regenerates a static triangle collision shape. `TerrainProbeView` installs the mesh and collision together after generation succeeds. A rough brown `SimpleMaterial`, explicit diagonal directional light and finite-difference surface normals make crater slopes readable; visual acceptance still needs target-device review.

The non-AR `RealityView` uses a virtual camera. The installed SDK declares this interface available in iOS 18 and macOS 15. This prototype establishes API and build feasibility only. It does not measure iPhone 12 or iPad (9th generation) acceptance, sustained frame pacing, memory pressure, collision physical response on acceptance hardware, or terrain drag hit testing. A dynamic sphere and contact event subscription now exercise physical collision response in the running sample; targeted taps exercise collision hit testing.

## Input and timing

“Drill next crater” walks a deterministic 5 × 5 sequence so identical commands can be repeated across devices. “Reset terrain” restores flat geometry. Controls are disabled during collision generation and guarded against overlapping updates. Accessibility identifiers are `terrain.drill`, `terrain.reset`, `terrain.surface`, `terrainStatus`, `terrain.collision`, and `terrain.settled`. The measurement callback includes a successful update revision and mesh/collision elapsed milliseconds. Collision timing includes asynchronous waiting; the callback is not a GPU or frame pacing measurement. Initial construction is also reported. A separately retained `SceneEvents.Update` subscription supplies monotonic timestamps for scene update cadence, which is not GPU presentation pacing. Pause suppresses input, callbacks and physics motion; resume preserves pose/velocity and restarts the settling observation timer. Disappearance cancels both retained subscriptions. Paused or failed regeneration rolls simulation and drop center back to the displayed terrain.

A generated `CollisionComponent` plus `InputTargetComponent` enables targeted surface tap/click input on iOS 18 and macOS 15. The targeted spatial tap performs a collision `hitTest` at its 2D location, filters to the terrain, converts the world hit into terrain coordinates, and digs there. The visionOS `location3D`/`convert` example does not compile on either of these targets; the installed SDK’s `hitTest` API does. A fresh cyan dynamic sphere drops above the last dig/tap center after every successful rebuild, against a static terrain physics body; reset drops it over the center of the flat grid. Both bodies use zero restitution and friction 0.8. Horizontal translation and rotation are locked so this is a vertical surface collision probe. A retained `CollisionEvents.Began` subscription reports contact x/y/z, dig center and revision. No contact log means collision response has not been observed; compilation alone is not a physics result. Drag gestures remain unimplemented. The heightfield cannot represent overhangs, cavities, disconnected chunks, or volumetric removal; it probes a surface excavation fallback.

## API choices and follow-up

[`MeshDescriptor`](https://developer.apple.com/documentation/realitykit/meshdescriptor) provides a small CPU-generated baseline. Apple’s [interactive geometry guide](https://developer.apple.com/documentation/realitykit/generating-interactive-geometry-with-realitykit) describes `LowLevelMesh` and Metal compute for faster dynamic updates. No compute extension is justified without measurements demonstrating that this simpler path misses an agreed budget. Increase grid size/update frequency only after recording device, OS, mesh and collision percentiles, frame pacing and memory. If collision regeneration dominates, investigate lower-resolution collision or less frequent rebuilds while preserving truthful input behavior.

## Collision diagnostic refinement

A first `CollisionEvents.Began` pose did not establish the settled excavation height in simulator testing. The prototype records first contact separately from a once-per-revision observation after at least one active second, requiring linear speed below 0.02 scene units/second and height remaining within 0.002 scene units of the initial stable height continuously for 0.75 seconds. Any speed or height excursion resets the stability window. While waiting, one-second diagnostics report pose, speed and elapsed active observation time. Resume restarts this timer. The sphere now locks horizontal translation and rotation so it acts as a vertical collision probe over the excavated patch rather than rolling out of it. Collision generation uses the current simulation positions and 16-bit triangle indices directly, separately from the rendered mesh. The latest iPhone 12 simulator run reported revision 2 contact at y = −0.006, x/z = −0.480, below the flat-surface sphere center baseline of 0.060. This demonstrates contact with the excavated patch in that run. The earlier instantaneous low-speed detector falsely classified a bounce apex at y = 0.127 as settled; the stronger sustained-rest detector subsequently passed on both the iPhone 12 and iPad (9th generation) simulators, reporting revision 2 sphere rest at y = −0.007. The final phone host/layout repeat also passed. This sequence does not establish caching as the cause of the earlier results. Physical hardware acceptance remains pending. The [Spike 00 evidence report](../../roadmap/audits/spike-00-platform-baseline.md) records the integrated results; retained [phone](evidence/iphone12-ios26-rest.txt) and [tablet](evidence/ipad9-ios26-rest.txt) logs provide the simulator rest observations.
